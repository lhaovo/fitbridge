## 二、风险登记表

| ID | 风险 | 概率 | 影响 | 缓解措施 | 触发信号 |
|----|------|------|------|---------|---------|
| R1 | **逆向接口随时失效**（迈金/顽鹿改版） | 高 | 高 | ① 接口健康探针每日自动探测；② 适配器版本化 + fixture 回归；③ 失败快速降级并告警；④ 优先把官方 API 平台做深 | 探针连续失败 / 上传返回结构变化 |
| R2 | **账号风控**（429、验证码、封号） | 高 | 高 | ① 每平台独立令牌桶 + 登录最小间隔；② 熔断；③ 绝不并发轰炸；④ 用户可手动调低频率；⑤ 提供「保守模式」 | 出现验证码 / 429 / 登录被拒 |
| R3 | **Strava 2026 政策**（订阅门槛、单 athlete、5.16 中转禁令） | 高 | 中-高 | ① 用户级 client_id/secret 优先；② 系统级共享仅作兜底且明确标注；③ 绝不跨用户流转数据；④ 数据流审计日志；⑤ 法务声明页 | 应用创建被拒 / 收到 API 违规通知 |
| R4 | **数据正确性**（时区、坐标系、FIT 损坏） | 中 | 高 | ① 规范化层统一处理并**记录 flags**；② UI 明确展示「此数据已做时区校正 / 坐标转换」；③ 原始文件与修正版并存可对比；④ 真实样本回归测试 | 用户报告时间偏差 / 轨迹偏移 |
| R5 | **FIT 解析能力不足**（TS 生态弱于 Java SDK） | 中 | 中 | ① TS 实现为主；② Java sidecar 兜底疑难文件；③ 收录真实异常样本库 | 某平台文件解析失败率上升 |
| R6 | **凭证泄露** | 低 | 极高 | ① 信封加密 + 主密钥外置；② API 永不返回敏感字段；③ 日志自动脱敏；④ 密钥轮换命令；⑤ 审计日志 | 异常导出行为 / 密钥告警 |

## 三、关键设计决策记录（ADR 摘要）

### ADR-001：服务端形态而非纯前端

- **背景**：逆向接口需长期持有 token、需要定时任务、CORS 限制
- **决策**：后端服务 + Web 前端，自托管 Docker Compose 为默认形态
- **代价**：用户需有服务器（NAS / VPS 均可）
- **备选**：桌面 Agent（备选实现，核心引擎可复用）

### ADR-002：适配器插件化 + manifest 声明能力

- **背景**：参考项目用两个枚举硬编码能力，扩展时易漏改
- **决策**：`PlatformAdapter` 接口 + `PlatformManifest` 声明式描述，前端直接由 manifest 渲染
- **收益**：新增平台不改引擎；UI 能力矩阵自动正确

### ADR-003：中间模型 + 原始文件双轨保存

- **背景**：各平台数据质量差异大，直接上传会丢信息或产生错误
- **决策**：同时保存「原始文件」与「规范化后的活动指标」；上传时按目标平台需要选择或转换
- **收益**：可追溯、可回放、可对比；用户能自己判断是否信任转换

### ADR-004：TypeScript 单体仓库（pnpm workspace）
- **背景**：需要前后端同构 + 适配器可独立测试
- **决策**：TypeScript 全栈，pnpm workspace monorepo，packages/core 不依赖任何平台代码
- **收益**：一套类型定义贯穿 API、引擎、适配器、前端

### ADR-005：中间数据不喂给大模型
- **背景**：Strava API 政策 5.3 禁止将 API 数据喂给 LLM context window
- **决策**：若未来接入 AI 功能，服务端按数据来源标记强制拦截 Strava 来源
- **备注**：当前版本不实现 AI 功能，此决策为预留护栏

## 四、需要用户决策的问题

> 这些问题会实质影响 M0 的实现方向，建议在开工前确认。

### Q1：部署形态优先级

| 选项 | 说明 | 影响 |
|------|------|------|
| A. **纯自托管（Docker Compose）** | 用户自己部署，数据完全自控 | 实现最简单，合规压力最小 ✅ **推荐** |
| B. 自托管优先 + 官方托管版 | 提供 SaaS，一键注册 | 需要多租户隔离、计费、运维，工作量 ×2 |
| C. 桌面 Agent | 装在用户电脑上 | 需要打包分发、跨平台、自动更新 |

### Q2：首批平台范围

- **最小可行（M0）**：迈金/OTM（源+目标） + MyWhoosh（源） + Strava（目标）
  → 覆盖「国内骑行数据 → 国际平台」这一最典型场景 ✅ **推荐**
- **加 iGPSPORT**：覆盖国内用户第二多的平台
- **加 Intervals.icu**：覆盖训练计划类数据，官方 API 最规范

### Q3：是否接受逆向接口

迈金/顽鹿 OTM 和 MyWhoosh 都**没有**面向第三方的公开 API，只有逆向。

- 接受 → 能覆盖国内主力平台（用户价值最大）
- 仅接受官方 API → 只能做 Strava / Intervals.icu / Suunto / COROS 等，
  国内用户基本用不上

**建议**：接受逆向，但在 UI 上明确标注「非官方接口」并要求用户确认，同时提供「只用官方 API」的合规模式开关。

### Q4：多用户 / 多租户

- 单用户自托管 → 简单很多，不需要 RLS、计费、审计
- 多用户 → 预留 `user_id` 字段即可，但 UI/权限/审计要额外做

**建议**：M0/M1 按单用户设计但全链路带 `user_id`（预留），M2 再做多用户后台。

### Q5：Strava 凭证模式

- 用户自填 client_id/secret（需每人注册 Strava 应用）→ 合规最好，但门槛高
- 系统提供共享 app → 门槛低，但受「单 athlete」「单 subscription」限制

**建议**：用户自填优先，系统共享作为可选兜底。

### Q6：FIT 技术路线

- 纯 TypeScript 实现 → 部署简单，疑难文件可能解析失败
- 引入 Java sidecar（Garmin FIT SDK）→ 兼容性最好，部署复杂度上升

**建议**：M0 用 TypeScript 实现 + 真实样本回归；把 sidecar 作为 M2 的可选增强。

## 五、立即可执行的下一步

如果方向确认，M0 的开工顺序建议：

```
1. 初始化 monorepo + Docker Compose + CI（骨架）
2. packages/fitkit（FIT 解析/CRC/GCJ-02）—— 配合真实样本文件
3. packages/core 契约 + 领域模型 + Postgres schema
4. apps/server 骨架 + 凭证加密 + 认证
5. adapters/otm（首个完整适配器，验证架构可行性）
6. 同步引擎 v1 + BullMQ
7. apps/web 连接账号页 + 任务页
8. adapters/{mywhoosh,strava}
```

其中第 2 步和第 5 步是**最高风险**（FIT 解析深度、逆向接口细节），应最先启动并尽早验证。
